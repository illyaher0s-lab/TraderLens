# B3 Point-in-Time Data Protocol and Research Snapshot Freeze Implementation Plan

> For agentic workers: REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build B 模块阶段三的 point-in-time universe、data snapshot、OOS window deterministic generation、ResearchProtocolSnapshot freeze 前置能力。B3 的目标不是快速跑回测，而是保证任何正式历史验证都只使用历史当时可见的数据，不能使用当前候选池、当前标签、未来财务公告、未来成分或幸存者股票池。

**Mainline purpose:** The final system must support real-money trading decisions through validated strategies and next-trading-day action plans. B3 exists to prevent fake historical validation before money is at risk.

**Architecture:** B3 sits between B2 StrategyDraft and later B4/B5 backtest/OOS/Gate execution. It produces immutable, auditable protocol inputs:

* `BacktestUniverseSpec`
* point-in-time membership snapshots
* `DataSnapshotManifest`
* deterministic OOS window
* frozen `ResearchProtocolSnapshot`
* quality/degradation reports

B3 does not calculate P&L, does not generate signals, does not run Gate, and does not promote strategies.

**Tech Stack:** Python 3.11, Pydantic v2, SQLite, Parquet where existing project convention supports it, `unittest`.

---

## 0. Scope and fixed decisions

B3 implements:

1. Point-in-time universe membership protocol.
2. Data snapshot manifest and hash.
3. Historical daily status visibility: ST, suspension, limit up/down, tradability.
4. Financial announcement-date visibility protocol.
5. Deterministic OOS window generation.
6. ResearchProtocolSnapshot freezing service.
7. Time-consistency guard for filters and universe sources.
8. Degradation/failure reporting for missing data.
9. Compatibility with B1 append-only storage and B2 StrategyDraft.
10. Tests proving current watchlists and future data cannot enter formal historical validation.

B3 does not implement:

* strategy_core backtest execution;
* trade simulation;
* P&L metrics;
* base/stress cost result;
* control groups;
* Prototype Gate calculation;
* OOS budget reservation/deduction/cache;
* Signal Board;
* execution log;
* broker integration;
* real LLM integration;
* real-time/live market data;
* UI/API unless needed for contract tests.

Fixed decisions:

1. B3 is on the real-money mainline. It is not a demo mode and not a shortcut layer.
2. B3 must reject unsafe data rather than silently degrade into a fake-valid backtest.
3. Formal historical validation only accepts `BacktestUniverseSpec`.
4. `ForwardWatchlistSnapshot`, confirmed candidate symbol list, current tags, and manual current symbol lists are not formal backtest universes.
5. Financial records are visible by `ann_date`, not by reporting period end date.
6. Unknown `ann_date` means unusable for historical signals or filters.
7. Current board/sector/concept membership must not be backfilled into past dates.
8. Missing delisted coverage must be visible and must downgrade or reject formal validation depending on severity.
9. Data missingness must be fail-loud or explicitly degraded; no fill, no inference, no LLM guess.
10. OOS start/end cannot be user-supplied or LLM-supplied. It must be generated by registered deterministic rules.
11. B3 does not allow user to choose technical parameters. System rules decide.
12. B3 must not modify B1/B2 accepted contracts unless a stop condition is triggered and approved.
13. B3 must not modify A module storage or old stable contracts.
14. B3 must not write `prototype_passed` or any Gate result.
15. B3 uses zero LLM calls. All logic is deterministic Python.
16. Git checkpoint is mandatory after each task.

## 8. Cost and concurrency note

B3 uses zero LLM calls.

All B3 logic is deterministic Python.

No agent concurrency is required during implementation. Runtime B3 services should not require LLM concurrency. This preserves the global LLM concurrency cap of 2 and avoids multi-agent agreement illusion.

## 9. Real-money mainline reminder

B3 is not a reporting feature. It is the anti-fraud layer for historical validation.

A strategy cannot later give usable buy/sell plans unless its historical validation used only data visible at that historical time.

B3 must prefer rejecting a potentially good strategy over letting a fake-good strategy pass.
